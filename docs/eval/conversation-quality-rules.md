# 대화 품질 평가 규칙: AI는 최종 판단하지 않는다

- **작성일:** 2026-11-24
- **적용:** 이 저장소에서 대화(대사·흐름·결말)의 품질을 다루는 모든 평가와 프롬프트 수정
- **계기:** "마지막 반응은 수긍(concede)인데 결과는 결렬" 4판을 처음에는 구조적 모순으로 봤다. 실제 대화를 읽어 보니 캐릭터는 같이 가자는 작은 제안만 받아들였고 핵심 갈등은 남아 있었다 (appraisal-review.md §17.5, `appraisal-experience` 브랜치). 라벨과 자동 집계로는 모순처럼 보였지만, 전체 맥락에서는 납득 가능한 반응이었다

## 1. 원칙

1. **대화 품질의 최종 판단은 사람이 한다.** AI의 품질 의견은 참고 자료다. AI·코드가 대화 품질을 자동 합격·불합격으로 확정하지 않는다.
2. **사람의 평가도 절대적인 정답이 아니다.** 나중에 실제 플레이어 테스트로 다른 사람들도 비슷하게 느끼는지 확인한다.
3. **목표는 테스트 점수가 아니다.** 플레이어가 실제로 대화했을 때 캐릭터가 살아 있는 사람처럼 느껴지는 서비스다.

## 2. 책임 분리

| AI·코드가 맡는다 (자동 판정 가능) | 사람이 맡는다 (대화를 경험해야 판단 가능) |
| --- | --- |
| 장면 설정과 명백한 사실관계의 모순 | 실제 사람처럼 자연스럽게 말하는가 |
| 대화 기록·기억·상태 저장의 정확성 | 윤재·서아의 성격과 가치관이 대사에 드러나는가 |
| JSON 형식, 실행 오류 | 플레이어의 말에 적절하게 반응하는가 |
| 명백한 발화 주체 혼동 | 다섯 마디 동안 감정과 갈등이 납득 가능하게 진행되는가 |
| 반복·질문 빈도, 비용, 지연 시간 같은 객관 지표 | 이전 경험이 대화에 자연스럽게 반영되는가 |
| 특정 현상이 생긴 코드·프롬프트 원인 추적 | 마지막 반응과 결말을 함께 봤을 때 이해할 수 있는가 |

- 말투 패턴 검사(`tonecheck`) 같은 자동 지표는 **사람이 어디를 읽을지 고르는 용도**다. 개수만으로 품질을 결론 내리지 않는다.
- 라벨(`concede`, `counter`, 장부 상태 등)만으로 품질이나 모순을 결론 내리지 않는다. 실제 대사를 확인한다.

## 3. 평가 단위: 5마디 전체를 하나의 경험으로

- 개별 마디 비교와 별개로, **5마디 전체의 흐름을 직접 평가하는 것**을 중요하게 다룬다.
- 각 대사가 따로 보면 자연스러워도, 전체를 보면 해명을 반복하거나 갑자기 마음이 풀리거나 앞선 감정과 맞지 않을 수 있다.
- 내부 출력(`heard`, `shift`, `want`, `thought` 등)의 비교는 원인 분석 자료다. 품질 평가의 대상은 플레이어가 보는 대화다.

## 4. 평가 자료의 형식 (AI가 준비한다)

AI의 역할은 대화가 좋다고 대신 결론 내리는 것이 아니라, 사람이 판단할 수 있게 자료를 준비하는 것이다. 기존 전사본과 Markdown 평가표를 재사용한다. 대시보드는 만들지 않는다.

- 실제 플레이어 발화와 NPC 대사를 포함한 **전체 전사본**
- 어색한 마디를 짚을 수 있는 **번호** (예: R3-2 = 3번 판의 2마디)
- 간단한 평가 항목: **말투 / 반응 적절성 / 감정 흐름 / 결말** (○ 괜찮음 · △ 애매 · ✕ 어색)
- 이유를 자유롭게 적는 **메모**. 다 채우지 않아도 되게 만든다
- **내부 상태·장부·점수·속마음은 별도 파일**로 두고, 평가가 끝난 뒤에 연다
- 자료의 한계를 맨 위에 적는다 (모델, 프롬프트 버전, 대본 고정 여부 등)

## 5. 순서: 사람이 먼저 읽고, AI는 그 뒤에 분석한다

1. A/B 비교에서는 **조건과 내부 해석을 가린다.** 대사만 무작위 순서로, 번호를 붙여 보여 준다.
2. 사람이 평가한다.
3. 평가를 받은 **다음에야** 정답 키와 내부 상태를 공개한다.
4. AI는 사람의 평가와 내부 상태를 비교해 원인을 분석한다.

AI는 사람이 평가하기 전에 자기 품질 분석이나 조건별 집계를 먼저 보여 주지 않는다. 객관 정보(모델, 실행 횟수, 비용, 실행 오류)는 먼저 보여 줘도 된다.

## 6. 사람의 피드백은 수정 명령이 아니라 관찰 데이터다

예: "여기서 윤재가 너무 쉽게 사과한다" → 곧바로 "이런 상황에서는 사과하지 마" 같은 규칙을 프롬프트에 넣지 않는다. 먼저 왜 그 반응이 나왔는지 확인한다.

| 확인할 원인 | 확인 방법 |
| --- | --- |
| Core에 저항·입장의 근거가 부족한가 | Core에서 그 상황의 가치·두려움이 적혀 있는지 본다 |
| 이전 경험·기억이 전달되지 않았나 | 그 마디 프롬프트에 앞선 대화·해석이 들어갔는지 본다 |
| BAND·move·검증기가 반응을 제한했나 | 그 마디의 끝맺음 지정, 점수 구간 묘사, 거부된 시도를 본다 |
| 1차 기록이 틀렸나 | 장부의 정리 상태와 근거 인용을 본다 |
| 모델 한계인가 | 같은 입력을 배포 모델(Terra)로 소량 돌려 본다 (docs/eval/testing-tiers.md 3층, `yunjae-tone` 브랜치) |
| 생성 변동인가 | 같은 입력을 여러 번 돌려 얼마나 자주 나오는지 본다 |
| 대본 탓인가 (리플레이) | 고정된 플레이어 말이 새 대사와 어긋났는지 본다 |

원인을 확인한 뒤에 **가장 작은 수정**을 한다. 상황별 정답 대사나 예외 규칙은 추가하지 않는다 (character-intent.md I5).

## 7. 개발 순환

**실제 대화 확인 → 사람이 품질 평가 → AI가 원인 분석 → 최소 수정 → 다시 실제 대화 확인**

- 새 실험을 계속 더하기보다, 지금 있는 실제 대화를 읽고 가장 중요한 문제부터 확인한다.
- 프롬프트를 고치면 무엇을 왜 바꿨는지, 전후에 무엇이 달라졌는지 남긴다.
